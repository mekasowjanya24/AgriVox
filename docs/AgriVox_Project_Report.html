1. Executive Summary & Problem Statement

1.1 Project Title & Pitch

AgriVox is an offline-first, bilingual (Telugu & English) Progressive Web Application designed for Indian smallholder farmers. It combines hands-free voice expense logging, real-time crop profitability analytics, and statistical machine learning mandi price forecasting with an intelligent Sell-Time Decision Advisor.

1.2 Problem Statement

Indian agriculture sustains more than 58% of rural livelihoods, yet smallholder and marginal farmers operate in severe financial vulnerability due to three systemic bottlenecks:

  • Lack of Real-Time Bookkeeping: Farmers incur recurring cash expenditures across seeds, fertilizers, chemical sprays, diesel, tractor hire, and daily coolie labour over a 4 to 6-month crop cycle. Because bookkeeping is manual or non-existent, farmers only evaluate financial health at season-end, often miscalculating net earnings and falling into predatory informal debt cycles.
  • High Friction of Existing Digital Tools: Existing agricultural mobile applications rely on dense text forms, complex menus, and English-only terminology. For rural farmers aged 35–60 with low digital literacy and calloused hands working in muddy fields, typing alphanumeric characters on touchscreens is impractical.
  • Asymmetric Market Information & Distress Sales: Farmers routinely harvest crops during regional glut periods and immediately sell produce at whatever price local commission agents offer. Without reliable price trend forecasts and storage trade-off calculations, they fail to capture post-harvest price recovery, losing an estimated 15%–30% in potential farm income.
  • Unreliable Rural Connectivity: Farmland and agricultural procurement yards frequently lack 4G/5G mobile connectivity. Cloud-only applications freeze, fail to save critical entries, and create data loss anxiety.
The AgriVox Solution: AgriVox solves all four challenges through: (1) Voice expense recording in conversational Telugu and English under 10 seconds; (2) An offline-first reactive IndexedDB store that queues writes with zero duplicates; (3) Live per-cycle and per-acre financial aggregations; and (4) A 14-day SARIMAX/Holt-Winters price forecasting engine that compares projected peak prices against warehouse storage holding costs to deliver clear "Sell Now" or "Wait N Days" advice.

4. End-to-End System Architecture

AgriVox implements a distributed, decoupled tri-tier architecture with an offline-first client tier, an Express REST API business logic tier, a dedicated Flask Machine Learning forecasting microservice, and a MongoDB persistence tier.

Figure 4.1: AgriVox Distributed Tri-Tier Architecture

4.1 Data Flow Across Tiers

  1. Client Interaction & Voice Transcription: The farmer dictates an expense into the mic. The browser's native Web Speech API processes audio locally or via OS speech providers. voiceParser.js extracts numerical and categorical entities.
  2. Local Write & Immediate UI Update: If offline or online, the expense is immediately inserted into Dexie IndexedDB with an ephemeral clientId (UUIDv4) and queued into db.outbox. The UI reacts instantly (0ms network latency).
  3. Asynchronous Synchronization: The SyncEngine detects network connectivity, batches outbox writes, and transmits them to /api/sync/pull. The server upserts records via Mongoose using partial filter expression unique indexes on (userId, clientId).
  4. Predictive Advisory Pipeline: When the farmer opens the Mandi Prices page, Express checks MongoDB for fresh forecasts. If older than 24 hours, Express transmits the historical price series to the Flask ML microservice (Port 8000), which trains candidates, calculates holdout MAPE, generates a 14-day forecast, and returns confidence bounds. Express executes the sell-time optimization algorithm and delivers the final advice to the React UI.

6. Database Design & Entity-Relationship Diagram

AgriVox utilizes MongoDB for flexible hierarchical document storage. Strict referential relationships and indexing rules guarantee data integrity across devices.

Figure 6.1: AgriVox Entity-Relationship (ER) Diagram

6.1 Mongoose Collection Specifications & Index Strategy

1. User Collection (users)

  • _id: ObjectId (Primary Key)
  • phone: String (10 digits), Unique Index
  • passwordHash: String (bcrypt salt 10 hash)
  • name: String (Farmer full name)
  • role: Enum ['farmer', 'admin'] (default: 'farmer')
  • language: Enum ['te', 'en'] (default: 'te')
  • storageCostPerQuintalPerDay: Number (default: 2.0 INR)
  • isActive: Boolean (default: true)

2. Plot Collection (plots)

  • _id: ObjectId (Primary Key)
  • userId: ObjectId → User._id (Required, Indexed)
  • clientId: String (UUIDv4 generated by offline PWA client)
  • name: String (e.g., "ఉత్తర చేను (North Field)")
  • areaAcres: Number (> 0)
  • soilType: Enum ['red', 'black', 'sandy', 'loamy', 'clay']
  • village, district: String
  • Compound Partial Index: { userId: 1, clientId: 1 } with partialFilterExpression: { clientId: { $type: "string" } } prevents duplicate offline plot insertion without triggering null collision errors.

3. Cycle Collection (cycles)

  • _id: ObjectId (Primary Key)
  • userId: ObjectId → User._id
  • plotId: ObjectId → Plot._id
  • clientId: String (UUIDv4)
  • crop: String (e.g., "వరి (Paddy)", "ప్రత్తి (Cotton)", "మొక్కజొన్న (Maize)")
  • season: Enum ['Kharif', 'Rabi', 'Summer']
  • year: Number (e.g., 2025, 2026)
  • sowingDate: Date; expectedHarvestDate: Date
  • status: Enum ['active', 'harvested', 'closed'] (default: 'active')
  • Compound Partial Index: { userId: 1, clientId: 1 }

4. Expense Collection (expenses)

  • _id: ObjectId (Primary Key)
  • userId: ObjectId → User._id
  • cycleId: ObjectId → Cycle._id (Indexed)
  • clientId: String (UUIDv4)
  • category: Enum ['seeds', 'fertilizer', 'pesticide', 'labour', 'irrigation', 'machinery', 'transport', 'other']
  • item: String (e.g., "Urea 2 bags")
  • amount: Number (> 0, INR)
  • date: Date (default: now)
  • source: Enum ['voice', 'manual'] (default: 'manual')
  • Compound Partial Index: { userId: 1, clientId: 1 }

5. Harvest Collection (harvests)

  • _id: ObjectId (Primary Key)
  • userId: ObjectId → User._id
  • cycleId: ObjectId → Cycle._id
  • clientId: String (UUIDv4)
  • quantityQuintals: Number (> 0)
  • pricePerQuintal: Number (> 0, INR)
  • buyer: String; market: String
  • date: Date
  • Compound Partial Index: { userId: 1, clientId: 1 }

6. Price Collection (prices)

  • _id: ObjectId (Primary Key)
  • commodity: String (e.g., "Paddy", "Cotton", "Maize")
  • market: String (e.g., "Warangal", "Khammam")
  • district, state: String
  • date: Date
  • minPrice, maxPrice, modalPrice: Number (INR/Quintal)
  • Unique Compound Index: { commodity: 1, market: 1, date: 1 } ensures zero duplicate daily market entries during bulk ingestion.

7. Forecast Collection (forecasts)

  • _id: ObjectId; commodity, market: String
  • model: String (e.g., "SARIMAX(1,1,1)", "ExponentialSmoothing-HoltWinters")
  • mape: Number (Model validation error percentage)
  • generatedAt: Date (Index with 24-hour TTL caching)
  • points: Array of subdocuments: [{ date: Date, predicted: Number, lower: Number, upper: Number }]

8. RefreshToken Collection (refreshtokens)

  • _id: ObjectId; userId: ObjectId → User._id
  • token: String (Hashed cryptographic token)
  • expiresAt: Date (TTL Index set to 7 days for automatic cleanup)

7.2 Security & Middleware Implementation

  • Dual-Token Authentication Flow: Access tokens (JWT signed with HMAC-SHA256) expire in 15 minutes. Refresh tokens are stored in an httpOnly, SameSite=Lax cookie and stored in MongoDB. Refresh requests rotate the token, preventing replay attacks.
  • Rate Limiting (express-rate-limit): Configured on /api with high headroom in development and loopback exemption (127.0.0.1), while enforcing 2,000 requests per 15 minutes in production and 50 attempts per 15 minutes on /api/auth/login to prevent credential stuffing.
  • NoSQL Injection Defense (express-mongo-sanitize): Strips dollar signs ($) and dots (.) from request bodies and query parameters, neutralizing MongoDB operator injection.
  • HTTP Security Headers (helmet): Injects standard security headers (Content Security Policy, X-Content-Type-Options, Strict-Transport-Security, Frameguard).

8. MongoDB Aggregation Analytics Pipelines

Rather than loading thousands of raw records into Node.js memory and computing totals in JavaScript, AgriVox executes computation directly inside MongoDB's C++ aggregation engine. Below are the key pipelines implemented in server/src/controllers/analyticsController.js.

8.1 Overall Farm Summary Pipeline (getSummary)

const cyclesAgg = await Cycle.aggregate([
  // Stage 1: Isolate current farmer's cycles
  { $match: { userId } },

  // Stage 2: Join parent plot to retrieve acreage
  {
    $lookup: {
      from: 'plots',
      localField: 'plotId',
      foreignField: '_id',
      as: 'plot',
    },
  },
  { $unwind: { path: '$plot', preserveNullAndEmptyArrays: true } },

  // Stage 3: Join all expenses linked to each cycle
  {
    $lookup: {
      from: 'expenses',
      localField: '_id',
      foreignField: 'cycleId',
      as: 'expenses',
    },
  },

  // Stage 4: Join all harvest sales linked to each cycle
  {
    $lookup: {
      from: 'harvests',
      localField: '_id',
      foreignField: 'cycleId',
      as: 'harvests',
    },
  },

  // Stage 5: Project cycle totals
  {
    $project: {
      plotArea: { $ifNull: ['$plot.areaAcres', 1] },
      cycleExpense: { $sum: '$expenses.amount' },
      cycleRevenue: {
        $sum: {
          $map: {
            input: '$harvests',
            as: 'h',
            in: { $multiply: ['$$h.quantityQuintals', '$$h.pricePerQuintal'] },
          },
        },
      },
    },
  },

  // Stage 6: Roll up all cycles across the farm into final KPIs
  {
    $group: {
      _id: null,
      totalExpense: { $sum: '$cycleExpense' },
      totalRevenue: { $sum: '$cycleRevenue' },
      totalArea: { $sum: '$plotArea' },
      count: { $sum: 1 },
    },
  },
]);

8.2 Categorical Expense Breakdown Pipeline (getExpenseBreakdown)

const breakdown = await Expense.aggregate([
  // Stage 1: Filter by authenticated user (and optional cycleId)
  { $match: match },

  // Stage 2: Group by agricultural category and compute total amount
  {
    $group: {
      _id: '$category',
      total: { $sum: '$amount' },
    },
  },

  // Stage 3: Shape output and round currency to 2 decimal places
  {
    $project: {
      _id: 0,
      category: '$_id',
      total: { $round: ['$total', 2] },
    },
  },

  // Stage 4: Sort descending so largest expenditure categories appear first
  { $sort: { total: -1 } },
]);

11. Offline-First Architecture & Synchronization

11.1 Offline Architecture Components

  • PWA Service Worker: Generated via vite-plugin-pwa. Precaches core assets (HTML, CSS, JS, SVG, web fonts). Intercepts network fetches and serves cached resources when offline.
  • Client Storage (IndexedDB): Dexie stores plots, cycles, expenses, harvests, and outbox. Writes complete locally without blocking for network responses.
  • Outbox Queue & Idempotency: Every local write creates an outbox entry: { entity, op, clientId, payload, createdAt, attempts, status }. The clientId is a UUIDv4 assigned at creation.
  • Conflict Handling & Duplicate Prevention:
    • On reconnect, the client pushes outbox records to /api/sync/pull.
    • The server performs findOneAndUpdate matching on { userId, clientId } with upsert: true.
    • If an entry was already synced previously, the server updates the existing document instead of inserting a duplicate.
    • MongoDB Partial Filter Index: { userId: 1, clientId: 1 } uses partialFilterExpression: { clientId: { $type: "string" } }, avoiding MongoDB duplicate key errors on legacy null entries.

12. Machine Learning Forecasting & Selling Advisor

12.1 Price Dataset & Model Selection

The time-series dataset (data/prices_seed.csv) contains 6,024 daily modal price observations from Warangal and Khammam APMC Mandis across Paddy, Cotton, and Maize spanning 2020 through 2026. The ML service evaluates two candidate algorithms against a holdout window:

  • Candidate 1: SARIMAX(1,1,1)(1,0,1,7): Captures seasonality and weekly mandi trading volume cycles.
  • Candidate 2: Holt-Winters Exponential Smoothing: Employs additive trend and damped extrapolation.
  • Fallback: 7-Day Moving Average: Activated if series length < 30 points or numerical convergence fails.

12.2 Model Evaluation Metric (MAPE)

$$ ext{MAPE} = rac{100%}{n} sum_{t=1}^{n} left| rac{ ext{Actual}_t - ext{Predicted}_t}{ ext{Actual}_t} ight|$$

Historical models achieve an average MAPE of 4.8% – 7.2% across commodities, well within the target threshold of ≤ 10%.

12.3 Smart Selling Advisor Mathematical Formulation

The advisor evaluates whether waiting $d$ days ($d in [1, 14]$) generates enough price appreciation to overcome warehouse holding costs:

$$ ext{NetGain}(d) = ext{PredictedPrice}(d) - ext{CurrentPrice} - ( ext{StorageCostPerDay} imes d)$$

The system computes $ ext{MaxNetGain} = max_{d in [1,14]} ext{NetGain}(d)$ and selects the optimal day $d^*$.

  • If $ ext{MaxNetGain} > 0.03 imes ext{CurrentPrice}$ (3% hurdle rate):
    Recommendation: WAIT $d^*$ Days. Expected Extra Gain = $ ext{MaxNetGain} imes ext{Quantity}$.
  • Otherwise:
    Recommendation: SELL_NOW. Expected Extra Gain = ₹0.
Worked Numerical Example:
Current Paddy Price ($P_0$) = ₹ 2,250 / Quintal. Farmer Stock ($Q$) = 50 Quintals. Storage Cost ($C_s$) = ₹ 2.0 / Qtl / Day.
• Day 7 Forecast ($P_7$) = ₹ 2,380 / Qtl.
• 7-Day Storage Cost = $7 imes ₹ 2.0 = ₹ 14.0$ / Qtl.
• Net Gain on Day 7 = $2,380 - 2,250 - 14.0 = ₹ 116.0$ / Qtl.
• 3% Hurdle Threshold = $0.03 imes 2,250 = ₹ 67.50$ / Qtl.
Decision: Since ₹ 116.0 > ₹ 67.50, the Advisor recommends: "Wait 7 Days to Sell".
Projected Extra Net Profit: $50 imes ₹ 116.0 =$ ₹ 5,800 additional profit.

14. UI/UX Design Decisions for Rural Farmers

AgriVox was intentionally designed to feel like an intuitive tool crafted for rural agriculturalists rather than an overly complex corporate dashboard.

17. Technical Challenges Encountered & Resolutions

Challenge Encountered Root Cause Analysis Implemented Engineering Resolution
MongoDB Null Index Collisions (E11000) Compound sparse index on (userId, clientId) threw duplicate key errors when multiple records lacked a clientId. Migrated from { sparse: true } to { partialFilterExpression: { clientId: { $type: 'string' } } } across all models.
Slow CSV Mandi Price Ingestion Row-by-row findOneAndUpdate queries for 6,000+ records caused write lock contention, taking minutes to seed. Replaced with unordered batch upserts using Price.bulkWrite(operations, { ordered: false }), reducing ingestion time to < 2 seconds.
PDF Download Header Encoding (ERR_INVALID_CHAR) Setting crop names containing Telugu Unicode in the HTTP Content-Disposition header violated RFC 7230 character restrictions. Sanitized the filename using regex replacement (replace(/[^a-zA-Z0-9_-]/g, '_')) while preserving full Telugu script in the PDF body.
API Rate Limiting Starvation The 200 req / 15 min rate limiter was exhausted during rapid UI slider interactions and automated test runs. Added loopback/development IP exemptions, increased limits (10,000 in dev, 2,000 in prod), and debounced slider requests by 250ms on the client.
Mixed Telugu/English UI Display Seeded database fields stored bilingual strings (e.g. 'వరి (Paddy)'), causing mixed text regardless of selected language. Built formatBilingualText(text, lang) with regex pattern matching and an agricultural dictionary to extract only the active language.

19. Examiner Viva Voce Preparation Guide (26 In-Depth Q&As)

Q1: What is the core problem AgriVox solves that existing agri-apps do not?

Answer: Existing agri-apps require heavy alphanumeric typing, complex menus, and active internet connectivity. AgriVox enables voice-first bookkeeping under 10 seconds in native Telugu/English, operates fully offline with IndexedDB outbox syncing, and couples cost accounting with statistical price forecasting to advise farmers on optimal selling times.

Q2: Why did you choose a Progressive Web App (PWA) over a native Android application?

Answer: Smallholder farmers often have entry-level smartphones with limited storage. PWAs install instantly from the web browser without Google Play Store friction, require < 5MB storage, update automatically via service workers, and share a single codebase across Android, iOS, and desktop browsers.

Q3: How does the offline sync engine prevent duplicate records when reconnecting?

Answer: The client assigns a unique UUIDv4 clientId to every record when created offline. On reconnect, the server performs an upsert matching on { userId, clientId }. If the record already exists, it is updated rather than inserted again. MongoDB partial filter indexes enforce uniqueness on client IDs.

Q4: Explain the difference between access tokens and refresh tokens in AgriVox.

Answer: Access tokens are short-lived (15 minutes) JWTs sent in the HTTP Authorization header to authorize API calls. Refresh tokens are long-lived (7 days) cryptographic tokens stored in an httpOnly, SameSite=Lax cookie and saved in the database. When access tokens expire, the refresh endpoint verifies the cookie, rotates the token in the database, and issues a new access token without requiring the user to re-enter credentials.

Q5: How does the voice parser convert spoken sentences into structured expenses?

Answer: voiceParser.js takes raw transcript text from the Web Speech API and executes a four-step pipeline: (1) extracts numbers from digits or Telugu/English number words; (2) matches words against an agricultural keyword dictionary across 8 categories; (3) strips matched amounts and currency terms to isolate the item description; and (4) presents an editable confirmation card before saving.

Q6: Why did you use MongoDB instead of a relational database like PostgreSQL?

Answer: Agricultural bookkeeping involves semi-structured, evolving attributes across crop cycles, varied expense items, and time-series prices. MongoDB handles polymorphic expense schemas, provides native JSON serialization for offline sync, and offers a multi-stage aggregation pipeline that computes farm financials directly within the database engine.

Q7: What is the mathematical formula used by the Smart Selling Advisor?

Answer: For each future day $d in [1, 14]$, it calculates: $ ext{NetGain}(d) = ext{PredictedPrice}(d) - ext{CurrentPrice} - ( ext{StorageCostPerDay} imes d)$. If the maximum net gain across the 14 days exceeds a 3% hurdle rate ($0.03 imes ext{CurrentPrice}$), the system recommends waiting $d^*$ days; otherwise, it recommends selling immediately.

Q8: What forecasting models are implemented in the ML service?

Answer: The Flask microservice trains both a SARIMAX(1,1,1) model and an additive Holt-Winters Exponential Smoothing model on historical mandi prices, evaluating them on a holdout set to pick the lowest MAPE. If historical data is under 30 days or numerical convergence fails, it falls back to a 7-day Moving Average with trend extrapolation.

Q9: What is MAPE and why is it preferred over RMSE for mandi prices?

Answer: Mean Absolute Percentage Error (MAPE) expresses forecast errors as an intuitive percentage relative to actual values. Unlike RMSE, which is scale-dependent and produces larger absolute errors for high-value crops (e.g. Cotton at ₹7,000/Qtl) versus lower-value crops (e.g. Maize at ₹2,000/Qtl), MAPE provides a standardized accuracy metric across all commodities.

Q10: How did you solve the MongoDB E11000 duplicate key error on compound sparse indexes?

Answer: Compound sparse indexes in MongoDB only skip index entries if all indexed fields are absent. If userId was present but clientId was null, the null value was indexed, causing duplicate key conflicts. We replaced sparse: true with a partial filter index: partialFilterExpression: { clientId: { $type: "string" } }, which only indexes documents with a valid string client ID.

Q11: Why is the ML forecasting implemented as a separate microservice?

Answer: Decoupling the Python statsmodels service (Flask on port 8000) from the Express API (Node.js on port 5000) prevents computationally intensive time-series model fitting from blocking the Node.js event loop. It also allows scaling the ML service independently.

Q12: How does AgriVox ensure full Telugu localization without font rendering issues?

Answer: The frontend uses i18next with structured JSON dictionaries and a bilingual formatter (formatBilingualText). For server-side PDF generation, PDFKit embeds the TrueType font NotoSansTelugu-Regular.ttf to correctly render complex Telugu conjunct glyphs without corruption.

Q13: What security measures prevent MongoDB injection in the Express server?

Answer: We use express-mongo-sanitize to strip dollar signs ($) and dots (.) from request bodies, preventing operator injection. Additionally, Mongoose schemas enforce strict data typing and schema validation.

Q14: How does the application handle rate limiting during development and production?

Answer: express-rate-limit applies a general limiter on /api and a strict limiter on /api/auth/login. In development, loopback addresses (127.0.0.1, ::1) are exempted to prevent developer lockout. On the frontend, slider inputs are debounced by 250ms to prevent rapid burst calls.

Q15: What happens if a farmer tries to delete a plot that has active crop cycles?

Answer: The backend checks for active cycles using Cycle.findOne({ plotId, status: 'active' }). If found, the delete request is rejected with HTTP 400 and an error message, preserving agricultural audit trails.

Q16: How are farm profits calculated per acre?

Answer: The aggregation pipeline computes: $ ext{NetProfit} = ext{TotalRevenue} - ext{TotalExpense}$. Total acreage is aggregated across plots ($sum ext{areaAcres}$). Profit per acre is calculated as: $ ext{ProfitPerAcre} = ext{NetProfit} / ext{TotalAcreage}$.

Q17: How did you optimize bulk mandi price CSV uploads from minutes to under 2 seconds?

Answer: We replaced sequential findOneAndUpdate operations with unordered bulk upserts using Price.bulkWrite(operations, { ordered: false }). This sends batch write commands to MongoDB in parallel, drastically reducing network round-trips.

Q18: What is the purpose of the clientId field across offline models?

Answer: clientId is a client-generated UUIDv4 assigned immediately when a record is created offline. It serves as an idempotent correlation key so that when the record is synced later, the server and client can match records without generating duplicates.

Q19: How does the Web Speech API handle browser compatibility fallbacks?

Answer: AddExpense.jsx verifies if window.SpeechRecognition || window.webkitSpeechRecognition is defined. If unsupported, the voice recorder is gracefully hidden and the manual entry form is displayed as the default view.

Q20: What are the primary touch target and accessibility constraints in AgriVox?

Answer: All interactive buttons and inputs have a minimum size of 48px × 48px to accommodate farmers with calloused hands. High-contrast earthy green (#1e4d2f) and warm cream (#fdfbf7) reduce glare in direct sunlight, and audio cues provide non-visual feedback.

Q21: How does the server prevent orphaned records when a cycle is deleted?

Answer: When a cycle is deleted, the controller runs: Promise.all([Expense.deleteMany({ cycleId }), Harvest.deleteMany({ cycleId })]) to cascade delete all associated expenses and harvest records.

Q22: Why does the forecasting engine use a 24-hour cache for predictions?

Answer: Mandi trading rates update once per day following APMC market closing. Re-fitting time-series models on every page load would waste compute resources. Daily caching in the Forecast collection ensures fast responses while reflecting fresh daily prices.

Q23: How does the frontend handle token expiration during active use?

Answer: Axios response interceptors in api/client.js catch HTTP 401 errors. The client calls /api/auth/refresh to exchange the refresh cookie for a new access token, updates the Authorization header, and retries the original request automatically.

Q24: What is the purpose of the source field on Expense documents?

Answer: The source field records whether an expense was logged via 'voice' or 'manual' entry. This enables tracking voice adoption rates in admin analytics to measure feature utilization.

Q25: How is Docker Compose configured for deployment?

Answer: docker-compose.yml coordinates four containers: mongo (database), ml-service (Flask on port 8000), server (Node.js on port 5000), and client (Nginx serving static PWA assets on port 3000), with health checks and restart policies configured for resilience.

Q26: What key lesson was learned from the bilingual text formatting issue?

Answer: Storing bilingual combined strings like 'వరి (Paddy)' directly in database records causes display issues when users select a single language. A proper localization architecture must either store canonical keys with client-side translation or include a parsing utility (formatBilingualText) to dynamically extract the active language's text.
